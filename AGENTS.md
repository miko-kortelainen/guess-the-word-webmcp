# AGENTS.md

Guidance for coding agents working in this repository.

`guess-the-word-webmcp` is a five-letter word guessing game with two interfaces to one game
state: a visual board for humans, and WebMCP tools for an agent running in the
browser. It is a submission to the OpenAI WebMCP Challenge (Devpost), which
constrains what may change and when. Read [Hackathon constraints](#hackathon-constraints)
before making structural changes or touching the deployed build.

## Commands

Node 20 or later.

```bash
npm install
npm run dev      # Vite dev server, prints the localhost URL
npm run build    # tsc --noEmit, then vite build
npm run preview  # serve dist/ with the WebMCP headers
npm run test     # vitest run
npm run test:watch
```

`npm run build` is the type check. There is no separate lint step, so run the
build before you claim a change compiles. Tests live beside the code they cover
as `*.test.ts` / `*.test.tsx`.

Word lists in `src/data/` are generated by `scripts/generate-wordlists.mjs`.
Edit the script, not the generated files.

## Architecture

```text
Human  →  React UI  ─┐
                     ├→  Game engine (plain TypeScript)  →  Solver
Agent  →  WebMCP tools ─┘         │
                                  └── change events → UI
                      tool-call records → activity log
```

Invariants. Breaking one of these is a design regression, not a refactor:

1. Neither the UI nor the tool layer implements game rules. Both call the
   engine (`src/game/engine.ts`).
2. There is one engine instance, created at module scope in
   `src/game/engineInstance.ts`. React subscribes with `useSyncExternalStore`.
   Engine state is never mirrored into `useState`.
3. Mode and authority are enforced in the engine, not only in the tool layer.
4. There is no tool that changes the collaboration mode. Only the human can.
   An agent that can grant itself submit authority has no authority model.
5. Tool output must not reveal the target word while the puzzle is in play.

### The five tools

Defined in `src/webmcp/tools.ts`, registered by `src/webmcp/register.ts`.
Feedback is a five-character string: `G` correct position, `Y` present
elsewhere, `.` absent. Positions are 1-based.

| Tool | Effect | Blocked when |
| --- | --- | --- |
| `get_game_state` | Read-only board state and clues | never |
| `suggest_guesses` | Ranks candidates, optional `count` 1–5 | never |
| `propose_guess` | Stages a word for human approval | observe-only |
| `submit_guess` | Plays a word | co-pilot, observe-only |
| `new_game` | Random puzzle, keeps mode | never |

| Mode | Read tools | `propose_guess` | `submit_guess` |
| --- | --- | --- | --- |
| Observe (`solo`) | yes | `mode_restricted` | `mode_restricted` |
| Co-pilot (default) | yes | stages a card | `approval_required` |
| Autonomous | yes | stages a card | plays the word |

Conventions when adding or editing a tool:

- Wrap `execute` in `logged(...)` so the call reaches the activity log.
- Return a JSON string, never an object.
- Validate and clamp input by hand. Do not trust `inputSchema` to have been
  enforced by the caller.
- `execute` may be called without the second options argument by the Chrome 149
  inspector. Keep it optional.
- Every `registerTool` call is awaited, rejections are caught, and an
  `AbortController` unregisters on React StrictMode cleanup. Keep that shape.
- `untrustedContentHint` is deliberately unset on every tool: all returned
  strings originate in this repository's own code and word lists. If you
  introduce user-generated content or a network fetch, set the hint.

## Deployment

Pushes to `main` deploy to GitHub Pages via `.github/workflows/deploy.yml`.

WebMCP stays silent unless the origin sends `Origin-Agent-Cluster: ?1`. GitHub
Pages cannot set that header, so the agent interface needs Vercel (see
`vercel.json`) or another host that can. The Vite dev and preview servers set it
locally. Verify a deployment with:

```bash
curl -sI https://YOUR-DOMAIN | grep -i origin-agent-cluster
```

This build ships without an origin trial token. A token is optional insurance
so the deployed origin works without the Chrome flag; neither judging path
below needs one.

## Testing WebMCP

In this order. The first environment is the one that decides the submission.

1. **ChatGPT desktop app, in-app browser.** WebMCP is enabled by default. Open
   the deployed HTTPS URL and ask the agent to inspect the puzzle, suggest a
   word, and propose it.
2. **Chrome 149+** with `chrome://flags/#enable-webmcp-testing` enabled, then
   relaunch. Open the same URL. Record the Chrome version in any write-up.
3. **Development only:** the Model Context Tool Inspector extension, which
   lists tools and calls them with JSON. It needs the Chrome flag even on
   Chrome 150+. Chrome DevTools also lists registered tools.

## Hackathon constraints

Source of truth is the official rules at
[webmcp.devpost.com](https://webmcp.devpost.com). This section is a working
summary of the parts that constrain the code; where it disagrees with the
official rules, the official rules win. Do not paste the full rules text back
into the repository.

### Dates (Pacific Time)

| Milestone | When |
| --- | --- |
| Registration and submission open | 25 Aug 2026, 11:00 |
| **Submission deadline** | **3 Sep 2026, 13:00** |
| Judging | 4 Sep – 21 Sep 2026 |
| Winners announced | on or around 23 Sep 2026, 14:00 |

**Freeze rule.** Once the submission period closes, do not touch the Devpost
submission, this repository, or the live site until winners are announced.
Editing any of them during judging risks eligibility. To keep building, fork
and work there. An agent asked to change this repo after the deadline should
refuse and say why.

### Hard requirements

- A working live URL reachable from the ChatGPT in-app browser or Chrome with
  WebMCP enabled. Free of charge, no restrictions, working through the end of
  judging. Credentials go on the submission form if the app authenticates.
- Public repository with all source, assets, and instructions needed to run it,
  plus an open-source licence file detectable in the repository About section.
  This repo is MIT; keep `LICENSE` at the root.
- The repository must contain a literal `document.modelContext.registerTool({...})`
  call with `name`, `description`, `inputSchema`, and `execute`. `src/webmcp/register.ts`
  and the README both carry it. Do not abstract that call away behind a wrapper
  that removes the recognisable shape.
- A public YouTube demo video under three minutes, with audio covering what was
  built and how WebMCP was used.
- Text description covering: why the use case fits WebMCP, how it improves the
  user experience, what humans and agents can now do together that was hard or
  impossible before, and briefly how WebMCP was implemented.
- Third-party SDKs, APIs, and data must be used within their licence terms.
  Word list provenance is documented in `src/data/WORDLIST_LICENSE.md`.
- Work must be original and solely owned by the entrant. One submission per
  entrant.
- Pre-existing work must be distinguished from work added during the submission
  period, with evidence such as dated commit history. Keep commits honest and
  descriptive.
- All submission material in English.

### Judging criteria, equally weighted

A pass/fail viability screen first: does the project fit the theme and
genuinely use WebMCP. Then:

1. **WebMCP leverage** — thorough, skilful, non-trivial, working use.
2. **Execution** — a complete, coherent product, not a proof of concept.
3. **Potential impact** — a specific, credible case for a real audience,
   actually addressed by what is demonstrated.
4. **Creativity and ambition** — novel concept, distinct from what exists.

Judges are not required to test the project. They may judge from the
description and repository alone, so the README and the live URL carry weight.
Prefer changes that make the working system legible over changes that only add
surface area.

## Known limitations

State these plainly rather than papering over them:

- WebMCP is an experimental, Chrome-oriented, origin-trial API. The entry point
  has already moved once: `navigator.modelContext` was removed, this app uses
  `document.modelContext`.
- The target word is in the client bundle. Tool output hides it during play.
  That is leak prevention through the agent interface, not a cheat-proof
  architecture.
- The suggestion engine is deterministic local code, not a language model. The
  app makes **no LLM API calls** and, after first paint, no network calls at
  all. There is no account and no backend.
- Tile contrast and keyboard access were designed in. The project does not
  claim WCAG conformance, and WebMCP is not an accessibility API. Do not add
  claims of an audit that has not happened.
